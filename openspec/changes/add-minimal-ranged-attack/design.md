# 设计

## 背景

现有 `AbilityComponent` 已提供目标能力的 CanActivate → Commit → Activate → End 生命周期，`MoveAbility` 已证明能力可以通过构造函数接收棋盘依赖。`GridLineOfSight` 只依赖 `ILineOfSightMap`，`GridLineOfSightMap` 可以实时读取 `GridManager` 的全障碍状态。战斗场景已有玩家单位选择、HUD、`Changed` 刷新事件，以及单位死亡时释放占格和注销回合的流程。本设计在这些边界上增加射击，不让 HUD 或输入代码重新实现战斗规则。

## 目标 / 非目标

**目标：**

- 用一个可独立测试的单位能力完成合法性检查、预览、AP 提交和一次攻击结算。
- 复用现有 LOS、属性、能力生命周期、死亡事件、棋盘占用和回合管理。
- 让目标列表和开火按钮只通过预览数据与控制器交互，不直接修改属性或查询障碍。
- 在目标或战斗状态改变时清除过期选择，保证开火按钮不会绕过最终合法性检查。

**非目标：**

- 不新增武器、弹药、装备、伤害类型、暴击或反击数据模型。
- 不实现攻击动画、特效、音效、掩体修正、高低差、战争迷雾或敌方 AI。
- 不把单位占用、半障碍或方向掩体改为 LOS 阻挡条件。

## 关键决策

### 1. 射击能力承载规则，战斗控制器承载流程状态

新增 `ShootAbility`，放在现有 Units 能力目录，构造时接收 `GridManager`，内部通过 `GridLineOfSightMap` 调用独立 LOS 求值器。能力的 `IsValidTarget` 负责单位类型、存活、敌我、棋盘登记、曼哈顿距离和 LOS；`AbilityBase` 继续负责标记、AP、回合内激活和独占能力检查。

`BattlePlayerController` 只保存当前己方单位和当前目标，枚举 `scene.SpawnedUnits` 后逐个请求能力预览，不复制射程、LOS 或阵营规则。正式开火仍通过 `AbilityComponent.TryActivate(ShootAbility, AbilityTarget.ForUnit(target))`，因此预览和执行使用同一套校验。场景层只在 `CanIssueOrders` 成立时允许玩家控制器调用能力，并只给玩家单位授予射击能力；敌方行为留给后续 AI。

备选方案是把射击判定直接写入 `BattlePlayerController` 或 `BattleSceneManager`，这样实现较快，但会让 UI/输入层依赖属性和棋盘细节，也无法复用到 AI 或其他攻击入口，因此不采用。

### 2. 用不可变预览数据隔离 UI 与属性公式

新增只读的攻击预览数据，至少包含目标单位、目标显示名、基础命中率和可用状态/失败原因。预览由 ShootAbility 计算且不修改属性；UI 只渲染目标名称和命中率。基础命中率为 Aim 减去 Defense 后限制在 0 到 100，Dodge 是命中后的擦伤概率，不改变 UI 展示的基础命中率字段。

攻击能力在 `OnActivate` 中使用两个独立的 0 到 1 随机值：第一个与基础命中率比较，第二个仅在命中后与 `clamp(Dodge, 0, 100)` 比较。普通命中伤害为 4，擦伤伤害为 2，最后按 `max(0, 伤害 - Armor)` 扣减 Health。伤害通过 `CharacterAttribute.ApplyBaseDelta(AttributeType.Health, -damage)` 进入现有 Health 归零和 `Unit.Kill` 流程。

为 EditMode 测试提供可选的随机值提供器；运行时默认适配 Unity 的随机源。这样不需要在测试中依赖概率，也不把随机实现暴露给 HUD。能力只在所有前置条件验证通过后提交 AP，结算阶段不再包含可能失败的地图查询，因此不会出现扣 AP 但攻击未执行的半提交状态。

### 3. 目标列表由控制器生成，HUD 只维护视图

扩展 `BattleHUD`，增加左侧目标列表容器、列表项按钮预制体、命中率文本和开火按钮引用。HUD 提供目标选择与开火请求事件；每次渲染时根据控制器传入的预览列表重建或更新列表项。列表项点击只回传目标，不直接激活能力；开火按钮点击才回传开火请求。

`BattlePlayerController` 在己方单位被选中、场景 `Changed`、棋盘 `Changed`、单位属性/标记变化或目标选择变化时刷新预览列表。它过滤掉不可用预览，并按 `UnitId` 稳定排序，避免同一帧目标顺序抖动。切换己方单位时清除当前攻击目标；点击列表项时只更新目标并让 HUD 显示命中率。开火按钮仅在目标预览有效、攻击者仍处于玩家命令窗口且 AP 至少为 1 时显示并启用。

备选方案是让 HUD 自己遍历单位并读取属性，但会把战斗规则复制到表现层；不采用。首版动态列表采用简单的实例化/销毁或复用现有按钮对象，目标数量较少时无需引入复杂虚拟列表。

### 4. 用现有事件刷新，而不增加新的全局状态机

`BattleSceneManager.Spawn` 在授予 `MoveAbility` 的同时授予 `ShootAbility`，并继续监听 `AbilityActivated`、`AbilityEnded`、`Died` 和 `Destroyed`。死亡时沿用 `ReleaseUnit`：取消能力、结束回合、移除占格、从回合管理器注销并触发 `Changed`。控制器收到该事件后重新枚举目标并清除已死亡目标。

为了让命中率在 Buff 改变 Aim、Defense、Dodge 或 Armor 后及时刷新，场景管理器在生成单位时订阅其 `CharacterAttribute.AttributeChanged` 和 `TagComponent.TagChanged`，统一转发为已有 `Changed`；清理时解除订阅。这样不需要 UI 维护所有单位的订阅关系，也不会新增一套刷新总线。若项目后续已有更细粒度的战斗事件，可再替换该转发实现而不改射击能力契约。

### 5. 保持移动手势与射击确认分离

棋盘上的己方单位点击仍负责选择单位，拖动仍负责移动预览；目标选择只通过左侧列表完成。控制器在重新选择己方单位、开始移动或目标变为无效时清除攻击目标，并隐藏开火按钮。射击能力结束后能力事件触发场景刷新，控制器重新计算 AP 和目标列表。这样不会把“点击敌人”解释成隐式开火，也不会让一次拖动同时提交移动和射击。

## 风险 / 权衡

- **[固定射程和伤害可能需要快速调参]** → 将常量集中在 `ShootAbility`，预览和结算共用同一值；后续可迁移到数据资产而不改变 UI 契约。
- **[随机命中使 PlayMode 结果不稳定]** → 运行时随机源可替换为测试用固定提供器，测试同时覆盖必中、未命中和擦伤分支。
- **[每次状态变化重建目标列表会产生少量 UI 分配]** → 首版目标数量受棋盘规模限制，先采用简单列表；有性能数据后再引入复用或差量刷新。
- **[目标在预览后移动或死亡]** → 开火时再次调用能力完整校验；失败不提交 AP，并由 `Changed` 清除过期选择。
- **[当前 LOS 不考虑单位占用和半障碍]** → 沿用既有 `grid-line-of-sight` 契约，掩体和部分遮挡留给单独的规则变更。

## 迁移计划

1. 先新增能力、预览数据和 EditMode 测试，不改变现有移动流程。
2. 在场景生成时给玩家单位授予射击能力，并加入控制器/HUD 的目标面板；未配置目标面板时初始化校验应给出明确错误，避免运行时空引用。
3. 增加 PlayMode 流程测试后运行现有 EditMode 与 PlayMode 测试程序集。
4. 回滚时移除射击能力授予、目标面板连接和新增脚本；现有 LOS、移动、死亡清理和场景配置保持可用。
