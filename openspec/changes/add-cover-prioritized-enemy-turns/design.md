# Design

## Context

参见 `proposal.md` 的动机与 `specs/enemy-turn-ai/spec.md` 的行为契约。当前 `BattleTurnManager` 已在单位 `BeginTurn` 后发布阵营回合开始事件；`BattleSceneManager` 只向玩家授予移动和射击能力，并通过下一帧计数直接跳过敌方回合。移动和射击均采用 `CanActivate -> Commit -> Activate -> End` 生命周期，表现可能异步结束，也可能在没有表现组件时同步结束。

棋盘可达性已经提供路径成本和路径，射击预览已经提供包含方向性掩体修正的最终命中率。现有预览只能按单位当前占格计算，不能直接评估尚未移动到的候选格；候选掩体还需要判断“玩家从该方向攻击敌人”时敌人格子的防护，而不是敌人攻击玩家时目标所获得的防护。设计必须在不临时改动占格、不复制战斗公式的前提下完成这些只读试算。

## Goals / Non-Goals

**Goals:**

- 把敌方回合的生命周期编排与战术选择拆开，使简单策略可独立测试并可在未来替换为行为树或 Utility AI。
- 让候选格的 LOS、最终命中率和方向性掩体评估与实际移动、射击共用规则源，决策过程不修改战斗状态。
- 正确等待同步或异步能力结束，并在死亡、注销、取消、提交失败和清理路径上保证敌方回合恰好收敛一次。
- 保持选择顺序完全确定，避免集合遍历、Unity 对象发现顺序或帧时序改变结果。

**Non-Goals:**

- 不引入 Unity Behavior、第三方行为树、黑板资产或可视化节点编辑器。
- 不设计巡逻、警戒、侧翼、协同集火、撤退、技能组合或不同敌人性格。
- 不改变移动、射击、掩体、命中率、AP、相机与伤害表现规则，也不为 AI 建立绕过能力系统的快捷执行 API。
- 不在本次变更中加入胜负判定；一方没有存活单位时只保证敌方控制器不会卡住或越权行动。

## Decisions

### 1. 使用回合执行器加可替换决策策略，不直接引入行为树

新增一个场景级敌方回合执行器，负责订阅敌方阵营开始/结束、保存本轮敌人快照、顺序驱动单位、提交能力、等待完成及最终请求回合轮转。执行器只理解“移动、射击、无行动”这类不可变行动计划，不包含候选评分细节。

决策放入独立策略接口。第一版 `CoverFirstEnemyDecisionPolicy` 接收只读决策上下文并返回一个行动计划；上下文包含当前敌人、按回合注册顺序排列的存活玩家、棋盘查询、移动能力、射击评估器和本次决策已排除的失败签名。策略不持有跨帧状态，也不直接激活能力。

选择这一结构是因为当前只有两类行动和一套固定优先级，完整行为树会引入节点生命周期、黑板同步和异步节点适配成本。接口边界保留了未来替换策略的能力；届时行为树只需产生相同的行动计划，无需重写回合执行与能力等待。

### 2. 抽取共享的只读射击评估，支持假设攻击者坐标

从 `ShootAbility` 当前私有评估路径提取无副作用的射击评估服务。输入显式包含攻击者、假设攻击者格、目标及目标实际格、射击配置快照、LOS 地图和目标命中率修正来源；输出沿用射击预览所需的合法性、距离、实际射线起点和不可变命中率 Breakdown。

实际 `ShootAbility.GetPreview` 与提交前重验调用同一服务，并传入攻击者当前登记格。敌人策略评估移动候选时传入候选格，但不改变 `GridCell.Occupant`、Unit Transform、Buff 或 AP。服务仍按既有当前格及四个正交探头格检查 LOS，并用候选格到目标实际格计算距离和方向性命中修正。

备选方案是让 AI 临时 `TryMoveUnit` 到每个候选再调用预览，然后回滚。该方案会触发棋盘事件、掩体 Buff、UI 和占格副作用，异常时还可能无法回滚，因此不采用。另一方案是在 AI 内复制射击公式，会使预览与提交逐渐分叉，也不采用。

### 3. 用共享方向规则从候选格读取防守掩体

把“从攻击者实际格到防守者实际格确定受保护边”的计算收敛为无状态方向规则。实际射击的 Cover modifier 解析和 AI 对候选敌人格的防守掩体评分都调用该规则。

AI 对每个“候选敌人格 + 玩家目标”组合读取候选 `GridCell` 的四边 CoverType：按玩家格相对候选敌人格的 X/Y 方向读取一至两个边，斜向取较高等级。这里评估的是玩家将来攻击该敌人时敌人获得的保护；敌人从候选格射击玩家的最终命中率则由共享射击评估器单独计算，二者不可混用。

当前格可以直接使用同一格数据评估，不依赖 `GameplayTag.InCover`。实际单位移动提交后，现有 `UnitCoverController` 仍负责把格子状态同步成 CoverBuff，最终玩家攻击时继续走正式 Buff 修正规则。

### 4. 候选生成固定为一个 AP 窗口并采用字典序比较器

策略使用移动能力的 `BudgetPerActionPoint` 取得一个 AP 的棋盘预算，并从可达结果中筛选成本不超过该预算的格子，同时把当前位置作为成本 0 候选。每个候选与每个存活玩家组合后，执行假设射击评估和防守掩体评估。

掩体射击候选必须同时满足：射击合法、防守掩体为 HalfCover 或 FullCover、移动计划合法且费用不超过 1 AP。排序键固定为：

1. 防守掩体等级降序；
2. 敌人射击该玩家的最终命中率降序；
3. 棋盘移动成本升序；
4. 玩家在回合注册表中的索引升序；
5. 候选 X 坐标升序；
6. 候选 Y 坐标升序。

选择一个 AP 窗口可以保证拥有 2 AP 的敌人在移动后保留射击费用，并让每次能力结束后重新决策。若敌人只有 1 AP，策略不会选择“移动后射击”的组合，因为预算校验还必须预留一次射击费用；它会优先执行当前位置合法射击，或在无法射击时进行一次改善位置的移动。

不采用加权总分，因为权重会让“全掩体必须优先”在极端命中率差异下失效，也难以从测试解释选择结果。

### 5. 无掩体候选时分两级降级

第一级从当前位置的全部合法射击中按最终命中率降序、玩家注册索引升序选择目标。0% 仍属于合法候选。这样严格落实“找不到掩体就选择命中率最高的玩家射击”，并且不会为了无关方向掩体放弃现有射击。

第二级仅在当前位置完全无合法射击时启用：先搜索一个 AP 内移动后能形成合法射击的非掩体格，沿用命中率、成本、目标索引和坐标的稳定排序；若不存在，则选择使“到任一存活玩家的最小整数格距”下降最多的可达格，再以移动成本和坐标打破平局。若最小距离没有严格改善，返回无行动，避免在等价格间来回移动。

移动计划不携带必须执行的后续射击命令。移动表现结束后执行器重新调用策略，因此目标死亡、占格改变、LOS 改变或掩体变化会自然得到最新决策。

### 6. 执行器通过能力结束事件推进，并防止同步完成丢事件

执行器在调用公共能力激活入口前，先订阅当前单位的能力结束事件并记录预期能力实例；激活返回后立即检查激活结果和能力 `IsActive`。这覆盖无视觉能力在激活调用内部同步结束、以及有视觉能力稍后异步结束两种情况。

成功且仍激活时，执行器停留在等待态；收到匹配能力的结束或单位失效通知后解除订阅，并在下一调度步重新读取完整状态。其他单位或其他能力的事件不能推进当前等待。采用显式状态机或协程均可，但事件是完成事实来源，不使用帧数、动画时长或轮询 Transform 判断。

执行器状态至少区分 Idle、Choosing、WaitingForAbility、Finishing、Disposed，并以本轮代号防止旧事件推进新回合。结束敌方回合前再次确认战斗仍在进行、当前阵营仍为 Enemy、没有正在等待的敌方能力且尚未为本轮请求过结束。

### 7. 提交失败必须有同状态熔断

能力计划在选择和提交之间仍可能失效。提交失败后，执行器重新决策，但把“单位、能力类型、目标或目的格、决策状态版本”组成的失败签名加入本次状态的排除集合。如果棋盘、AP、单位存活、目标或掩体状态均未变化，策略不得立即返回同一失败签名；没有其他计划时结束当前单位。

任一相关状态变化或成功能力结束后清空排除集合。这样保留对瞬时失效的恢复能力，同时避免同一个不可提交计划在一帧内无限重试。异常只记录诊断并安全结束当前单位，不回滚已经由能力提交的消耗。

### 8. 场景装配统一授予战斗能力并显式管理控制器生命周期

`BattleSceneManager` 生成 Player 和 Enemy 时都授予现有 Move/Shoot 能力及各自表现组件；玩家输入控制器仍只接受 Player，因此不会获得敌方单位控制权。场景显式引用敌方回合控制器，并在所有单位、棋盘、回合和配置准备完成后初始化它，再开始战斗。

删除 `skipEnemyAfterFrame` 和对应 `Update` 跳过逻辑。清理时先关闭敌方执行器，使其解除回合及能力事件，再取消单位能力和销毁单位，避免清理事件触发新决策。初始化校验确认 Enemy 预制体拥有移动与射击表现依赖、场景控制器可用，并继续复用当前 GameSettings。

## Risks / Trade-offs

- [候选数量等于可达格与玩家数的乘积，每次评估还包含多条 LOS] → 仅检查一个 AP 范围，先过滤不可达和无掩体格，并在单次决策中缓存格子、距离与 LOS 结果；当前地图和单位规模下保持同步确定性实现。
- [假设坐标评估与实际提交之间状态可能改变] → 候选只用于选择，移动后重新决策，实际能力提交始终执行完整重验。
- [方向性掩体变更尚处于一个未归档但已完成的 OpenSpec change] → 实现前确认 `add-directional-cover-buffs` 的代码、配置和测试仍在工作区；本变更不复制或替代其规则。
- [已经在掩体中的 2 AP 敌人可能连续射击两次] → 这是复用当前 AP 规则和“剩余 AP 继续决策”的明确结果；未来若射击需要结束单位行动，应作为统一能力规则或独立 AI 策略变更处理。
- [所有玩家死亡时缺少战斗结束规则] → 控制器把无目标视为无行动并安全结束敌方回合；胜负判定留给后续能力，避免本变更隐式扩大范围。
- [移动或射击表现的回调未到达可能阻塞回合] → 复用能力在禁用、取消和导航失败时必须结束的既有契约，并额外监听单位失效、阵营结束与控制器清理作为退出路径；不以超时伪造成功。

## Migration Plan

1. 先抽取共享方向性掩体规则和假设坐标射击评估器，迁移现有 `ShootAbility` 预览、提交与测试，确认玩家行为结果不变。
2. 实现纯决策模型与掩体优先策略，通过 EditMode 测试覆盖候选筛选、排序、最高命中率降级、推进和稳定平局。
3. 实现敌方回合执行器及同步/异步能力等待、失败熔断和清理，使用可控测试替身验证恰好一次轮转。
4. 统一 Player/Enemy 能力装配，接入场景控制器，移除下一帧跳过逻辑并补齐初始化校验。
5. 更新 Map1 场景引用，运行聚焦 EditMode、完整 EditMode 和敌方回合 PlayMode 场景测试，验证移动到掩体、射击表现、连续 AP 行动和返回玩家回合。

回滚时恢复场景及 Enemy 预制体引用、恢复临时敌方跳过逻辑，并移除敌方回合控制器与策略；共享评估器若已被玩家射击路径采用，应与对应 `ShootAbility` 修改和测试一并回滚，避免留下两套评估路径。
