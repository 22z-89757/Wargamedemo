# 设计

## 背景

参见 `proposal.md` 的“为什么”。当前 `GridLineOfSight.HasLineOfSight` 使用整数格坐标执行单条格心到格心的无状态 supercover 遍历；`ShootAbility.TryGetFiringOrigin` 则按当前格、下、右、上、左的固定顺序调用该查询。地图适配器只暴露格子是否存在及是否阻挡 LOS，且只有 `FullBlocked` 不透明。

这次调整必须继续使用纯逻辑棋盘数据，不引入 Unity Physics 或世界坐标查询，并保持预览与提交得到同一结果。

## 目标与非目标

**目标：**

- 以精确且确定性的方式判断“起点格心能否接触目标格任一顶点”。
- 保持现有 5 个射线起点、起点过滤和固定优先级。
- 保持中途格角的保守阻挡规则，同时把目标顶点作为终止成功点。
- 让算法测试不依赖 Unity 场景、Collider 或浮点容差。

**非目标：**

- 不改变 SightRange、距离计算、命中率、方向掩体或 `HalfBlocked` 的规则。
- 不增加边缘中点、单位模型轮廓或任意连续边界采样；本次终点集合严格为四个格顶点。
- 不改变视觉弹道的目标位置，也不记录命中的具体目标顶点。

## 决策

### 1. 保持格子级公开查询，内部改为四条终点射线

`HasLineOfSight(map, from, to)` 仍接收起点格和终点格，先保留空地图、越界和同格的快速判定，再依次检查从 `from` 格心到 `to` 格四个顶点的射线，任一成功即返回 `true`。因此 `ShootAbility` 现有起点循环自然形成最多 `5 x 4 = 20` 条射线，且 `TryGetFiringOrigin` 仍只需返回所选起点。

备选方案是在射击能力中显式枚举四顶点。该方案会把通用 LOS 的目标边界语义泄漏到战斗层，并使其他调用者继续得到旧的格心判定，因此不采用。

### 2. 使用放大两倍的整数坐标表达格心和格顶点

在内部几何坐标中，逻辑格 `(x, y)` 的中心表示为 `(2x + 1, 2y + 1)`，四个顶点表示为 `(2x, 2y)`、`(2x + 2, 2y)`、`(2x, 2y + 2)`、`(2x + 2, 2y + 2)`。射线遍历用整数或精确有理数比较跨越下一个网格边界的先后，避免浮点误差改变格角判定。

备选方案是使用 `Vector2` 与 epsilon。它更短，但顶点恰落在边界时容易因平台或运算顺序差异进入不同格子，不满足确定性要求。Unity Physics Raycast 同时依赖场景碰撞体，也与现有地图接口约束冲突。

### 3. 终点接触优先于终点外侧障碍检查

遍历只检查射线开区间中接触或穿过的中间格。若下一次边界事件就是指定目标顶点，则立即将该射线判为成功，不检查仅在该终点处相接的邻格；目标格自身与起点格自身仍不作为阻挡格。

对于抵达目标顶点之前的边界事件，继续采用现有保守规则：射线穿过共享角点时检查两侧相邻格，任一为 `FullBlocked` 即阻断；沿共享边界前进时也应确保边界任一侧的中间 `FullBlocked` 不能被贴边绕过。

备选方案是把目标顶点当作普通中途格角处理。它会再次因目标边缘外侧的墙体拒绝射线，违背“接触目标边界即成功”的规格。

### 4. 接受 LOS 的方向性，移除对称性假设

`A -> B` 使用 A 的格心与 B 的四顶点；`B -> A` 使用 B 的格心与 A 的四顶点，两者可能不同。实现不缓存或镜像反向结果。原有验证正反向相同的测试应改为分别验证每个方向遵循自身几何路径，并增加至少一个结果不对称的合法布局作为回归保护。

备选方案是要求双向任一可见或双向都可见。前者会扩大可见范围，后者会重新引入目标边缘不可见问题，均不符合从观察者出发的查询语义。

### 5. 保持起点选择与业务快照不变

射击层继续先查攻击者当前格，再按下、右、上、左检查正交相邻格；越界或 `FullBlocked` 起点仍被跳过。首个对目标任一顶点可达的起点成为 `FiringOrigin`。距离、命中率、AP 提交以及预览/结算一致性仍以双方实际占格与现有快照规则计算。

具体可达顶点无需写入 `ShootPreview` 或 `ShootResult`：它只影响布尔可见性，不参与现有视觉起点和伤害结算。这样可避免不必要的数据模型迁移。

## 风险与权衡

- [方向性变化会使依赖 LOS 对称性的旧测试或调用假设失效] -> 搜索所有调用点，替换对称性断言，并用正反向独立用例明确新契约。
- [顶点采样比单条格心射线更宽松，可能允许仅有一个点暴露的目标] -> 这是本次明确要求；仅采样四个顶点，不扩展到整条边界的任意点。
- [终点特判若过早执行，可能跳过真正位于目标前方的墙格] -> 测试“墙格仅共享终点”和“墙格在终点之前占据路径”两类相邻布局，终止条件只在精确抵达指定目标顶点时生效。
- [最多 20 条遍历增加查询成本] -> 每条遍历仍与格距线性相关且无分配；保持短路与固定顺序，避免构造临时集合。若后续性能数据表明有热点，再单独评估缓存。
- [整数坐标放大时可能溢出] -> 中间差值与乘积继续使用足够宽的整数或 `decimal`，并为大坐标边界补充单元测试。

## 迁移计划

1. 先补充 LOS 单元测试，覆盖任一顶点可达、四顶点全阻挡、中途格角和终点接触。
2. 调整通用 LOS 遍历并运行 EditMode 测试，确认地图适配器语义不变。
3. 更新射击能力测试，验证 5 个起点、固定优先级、距离快照与墙后边缘目标。
4. 运行相关 PlayMode 战斗流程测试，确认目标列表和预览/提交保持一致。

无需资产或存档迁移。若需回退，可恢复原格心到格心遍历及相应测试；其他数据结构不受影响。
